Builds go through EAS (`npx eas-cli@latest build --profile development|production --platform android|ios`). The development build loads JS from Metro, so JS-only changes need only a Metro reload; adding a package with native code, or changing native config in `app.json` (plugins, icons), needs a new build. `eas.json` uses `appVersionSource: remote` + `autoIncrement`: only bump `expo.version` in `app.json` by hand.

Android can be built on this laptop (JDK 17 and `~/Android/Sdk` are installed); iOS builds only on the cloud.
- Dev build: `npx expo prebuild --clean --platform android` (only after native config changes; `android/` is gitignored and our native code lives in `modules/` and `plugins/`), then `npx expo run:android`. It is signed with a local debug key, so uninstall an EAS-signed dev build first.
- Store build: `npx eas-cli@latest build --profile production --platform android --local` signs with the upload key stored on EAS and writes `build-<timestamp>.aab` to the repo root (gitignored). Never ship a plain Gradle release build: it carries the wrong key.

## Architecture

### Our backends, and which one to call

Outside data feeds (Nepal Rastra Bank forex, YoNEPSE market data) are listed in the map under "Backend contracts".

- **Supabase (anon key)**, `src/lib/api/supabase.ts` / `queries.ts`: public reads (articles, categories, tags, forex) protected by RLS, and the push-token RPCs. Never put a service-role key in the app.
- **Website API**, the sibling Next.js repo at `../../site/site` (deployed to a DigitalOcean droplet, not Vercel). Calls that need to know *who* the reader is send a Clerk session as `Authorization: Bearer`. Some routes are public (Chautari `discover` and room details, public profiles, newsletter, contact).
  - `/api/chautari/*` via `CHAUTARI_API_URL` (`https://api.icn.news`, `src/lib/api/chautari.ts`): rooms, join tokens, hands, moderation, banners, scheduling.
  - `/api/reader/*`, `/api/newsletter`, `/api/contact` via `SITE_URL` (`https://icn.news`, `readerProfile.ts`, `newsletter.ts`): profiles (including other readers' public profiles), follows, newsletter, contact desk.
  Since the migration off GoDaddy, both addresses reach the same Next.js process on the droplet. They stay separate variables so Chautari could move to its own host later; the comment in `src/constants/config.ts` describes that intended split, not today's setup.
  The server decides permissions; the app only displays them. Many features need a change in both repos.
- **Supabase Edge Functions + SQL** in `supabase/`: push senders (`send-breaking-push`, `send-chautari-live-push`, `send-reminder-push`) triggered by database webhooks or `pg_cron`. Production schema changes (here and in the site repo's `supabase/`) are still applied by hand in the Supabase SQL editor; there is no migration runner against production. This repo's hand-applied history is in `supabase/legacy-migrations/`; `supabase/migrations/` holds only the baseline dump the local stack is built from. When you change production's schema, add a new migration file here too so the local copy keeps up. Deploy order is always database → site → app.

### Identity

Clerk handles sign-in (email OTP only; `app/sign-in.tsx` silently fills the username/password Clerk requires). The reader's public identity is a `reader_profiles` row in Supabase (username, display_name, bio, avatar_url), read through `useMyProfile()`. A signed-in reader without a row is sent to `/profile/complete` by `ProfileCompletionGate` (mounted in `app/_layout.tsx`) and by the sign-in flow. `needsCompletion` is true only when the request *succeeded* and returned no profile (404 → `null`); a failed request is `isError`, never "no profile", or an offline reader would be sent to sign up. After signup `/profile/complete` goes back to where the reader came from. Anything the server labels with the reader's name at the moment it happens (a Chautari join token) must wait for the profile, or the name is "Guest" for good. Use `profile.display_name`, not Clerk's `fullName`/`firstName`, anywhere a name is shown.

Builds can run without Clerk configured (`isClerkConfigured`). Clerk hooks throw outside `<ClerkProvider>`, so screens use an outer component that returns a fallback when unconfigured and an inner `...Active` component that calls the hooks.

### Navigation

`app/_layout.tsx` is the root Stack plus providers (theme, persisted query client, bookmarks, active Chautari room, push nudge, Clerk). The five tabs live in the `app/(tabs)/` group, rendered by a Tabs navigator with its own bar hidden (`tabBar={() => null}`) so screens stay mounted; the visible bar is the custom `src/components/BottomNav.tsx`. New non-tab routes get a `Stack.Screen` entry in `_layout.tsx` for their animation.

Every screen that loads data distinguishes loading, not found (the server's answer: show `EmptyState` with a way out), failed (`ErrorState` with Try again) and empty. `ErrorState` always says "Connection issue", so don't use it for refusals or missing things. Back buttons use `router.canGoBack() ? router.back() : router.replace(...)`, because a screen opened from a link has no history. `app/+not-found.tsx` replaces Expo's "Unmatched Route" screen.

### Links (App Links, Universal Links, notification taps)

Vault note 22 explains the whole path.
- **Incoming links** from the OS (shared `https://icn.news/...` links, `icn://`) go through `app/+native-intent.tsx` → `systemLinkTarget` in `src/utils/deepLinks.ts`: web paths are rewritten to app routes (`/{section}/{story}` → `/article/{story}`, `/chautari/{slug}` stays), a path it can't read is returned unchanged and lands on `+not-found` (never hand an icn.news link back to the OS, which could loop, and don't open anything from the hook: on a cold start it runs before there's a screen), anything else passes through. It must never throw. There is no `Linking` listener in `_layout.tsx`: that used to open screens twice.
- **Notification taps** are not OS links: `navigateToUrl` in `_layout.tsx` calls the same `resolveDeepLink`. Specific prefixes (`chautari`, `search`, the reserved words) must stay ahead of the generic `/{section}/{story}` rule.
- **Which links open the app** is decided by the phone at install time:
  - Android: `android.intentFilters` in `app.json` (`autoVerify`, one `pathPrefix` per claimed path) plus the site's `public/.well-known/assetlinks.json` (package + SHA-256 of the app signing key, the previous key and the upload key; never the public debug key).
  - iOS: `ios.associatedDomains` (`applinks:icn.news`) plus the site's `public/.well-known/apple-app-site-association` (Team ID `R3647928BF`).
- Claimed paths (`/chautari/` and the 8 section slugs) live in three places that must agree: `app.json`, the Apple file, and the resolver. A new website section opens the website until an app release claims it.
- Publish the `.well-known` files only after the app version that handles them is live in both stores. Changing `intentFilters` needs a new native build.
- Without the app, room links land on the site's `/chautari/[slug]` page (store badges, `noindex`).

### Chautari (live audio rooms, LiveKit)

- The connection lives in `ActiveRoomProvider` (`src/features/chautari/ActiveRoom.tsx`), not the room screen, so leaving the screen keeps the audio (shown by `MiniRoomBar`). The screen calls `enter`/`leave`.
- `useChautariRoom.ts` turns LiveKit participants into `RoomMember`s. Server-set **metadata** (fixed per join: username, avatar, host) and **attributes** (change live: `hand`, `mod`) are parsed defensively there.
- Pattern: the site API writes the database record first, then updates LiveKit so every client sees it. A raised hand or a moderator appointment is visible because the server sets an attribute, not because the app holds local state.
- Rooms can be `scheduled` (waiting room, Go live by host or assigned moderator), `live`, or `ended`. Times are shown in Kathmandu time (`src/features/chautari/schedule.ts`).
- Room UI components are in `src/components/chautari/`.
- Live chat and applause arrive as LiveKit data packets the **server** sends (topics `chautari.chat` and `chautari.effect`); `useChautariRoom.ts` routes them to `useRoomChat` and `useRoomEffects`. The app never publishes data itself.

### Native-module seams

Some native modules are missing in Expo Go or on web, and importing them at module scope crashes the whole app. They are reached through guarded seams: `src/lib/notifications/module.ts` (expo-notifications), `src/lib/audio/module.ts` (expo-audio, the Chautari clap sound), and `src/lib/livekit/platform.ts` vs `platform.native.ts` (Metro picks per platform). Keep new uses behind these.

### Push notifications

Device tokens are registered through `SECURITY DEFINER` RPCs (`src/lib/api/pushRegistry.ts`); per-type opt-ins (Chautari, reminders) are columns on the token row and are replayed after every re-registration because re-registering resets them. `src/features/pushNudge/` is the soft-ask flow (tab dot, contextual sheet) that precedes the OS permission prompt.

### Articles (pre-existing)

- Only `status = published` rows are readable with the anon key (RLS). There is no app-side write path for content; the newsroom publishes through the site's `/admin`.

### Chautari

Tables (`site/supabase/2026-10-chautari.sql`, plus the moderators and scheduling migrations): `chautari_rooms` (slug, title, `status` `scheduled|live|ended`, `scheduled_for`, `host_clerk_id`, `max_participants` default 200, `banner_url`, counts), `chautari_participants` (room, Clerk id, role, `left_at`, removal), `chautari_speaker_requests` (raised hands), `chautari_host_entitlements` (who may host), `chautari_messages` (live chat, `site/supabase/2026-11-chautari-chat.sql`).

- **Who may host**: `CHAUTARI_HOSTING` on the site is `open` (default: any signed-in account unless a revoked entitlement row bars them) or `invite` (only accounts with an unrevoked entitlement row). Fails closed if the table can't be read. Refusal is `not_entitled_to_host` (403).
- **Joining** (`POST /token`): verify Clerk session → load room → read the stored role → enforce capacity and removal → mint a short-lived token whose grants come from the role. Refusals carry a `reason` the app branches on: `not_signed_in`, `room_not_found`, `room_ended`, `room_full`, `removed_from_room`, `not_entitled_to_host`, `room_not_started`. Moderation refusals: `not_host`, `room_ended`, `target_is_host`, `target_is_self`, `target_not_in_room`.
- **Presence** (`POST /webhook`, called by LiveKit, signature-verified): `participant_joined` / `participant_left` set `left_at` and counts; `room_finished` ends the room. Handlers set values rather than toggle, because events repeat and arrive out of order. This is what clears readers who force-quit or lose signal.
- **Invites** (`POST /invite` `{ slug, usernames }`, up to 10): host or assigned moderator (`decideInvite`), room booked-and-unexpired or live. Only readers who follow the caller with `notify` on are invited; the reply lists `invited`, `alreadyInvited`, `notReachable`. One row per person per room in `chautari_invites` (`site/supabase/2026-11-chautari-invites.sql`); its INSERT webhook fires `send-chautari-invite-push`. Rate limited per inviter.
- **Report and block** are offered on a person (tap them) and on a chat message (long-press it; the ⓘ in the chat explains this). Block is on-device only (`src/lib/storage/chautariBlocks.ts`): it silences that person's audio and hides their chat messages locally. Reports are below, under "Reports, word filter and suspensions".
- **Live chat** (`/api/chautari/chat`, Clerk bearer on every method): `GET ?roomSlug=` returns the last 50 messages oldest first (`{ messages, open }`, rate limited); `POST { roomSlug, text }` needs the writer in the room now (`decideChatSend`; refusals `not_in_room`, `removed_from_room`, `room_ended`, `room_not_started`, plus `empty`/`too_long` for the text, max 300 characters, 12 per 30 s), stores the row, then broadcasts it; `DELETE { roomSlug, messageId }` soft-deletes for the host, a moderator or the author. Messages carry `authorId` (the Clerk id, matching LiveKit identities and the block list). Rows are kept after the room ends; deleted ones keep `deleted_at`/`deleted_by`.
- **Applause** (`POST /api/chautari/effect { roomSlug, effect: "clap" }`): host or a moderator in the room, live rooms only (`decideRoomEffect`; refusals `not_host`, `room_ended`, `room_not_started`; 6 per minute). Nothing is stored; every app plays its bundled `assets/sounds/clap.m4a`.
- **Roles** live in `chautari_participants.role`: `host`, `moderator`, `speaker`, `listener`. The host is also recognised from `chautari_rooms.host_clerk_id`. Host, moderator and speaker get `canPublish`.
- **Moderation** (`POST /api/chautari/moderate`, actions `approve_speaker`, `deny_speaker`, `demote_speaker`, `mute`, `remove`, `make_moderator`, `remove_moderator`): allowed for the host or a moderator who is in the room. Nobody can act on the host or on themselves. Moderators have every host control, including ending the room.
- **LiveKit participant fields**, all set by the server: identity is the Clerk user id; name is the resolved display name; metadata is JSON `{ username, avatar, host }` fixed at join; attributes `hand` (set by `POST /hand` with `raised: true`; cleared by the listener with `raised: false`, or when the host or a moderator approves or denies) and `mod` (set by `make_moderator`, also minted into a moderator's token so it survives reconnects). The app reads these in `useChautariRoom.ts`.
- **Names**: `rooms` and `token` resolve the display name from `reader_profiles`, then a cleaned client value, then `"Guest"`. Never a raw `user_…` id.
- **Lifecycle**: `scheduled` → `live` via `POST /rooms/start` (host or an assigned moderator, no need to be present; a conditional update so a double tap starts once) → `ended` via `DELETE /rooms?slug=` (which also cancels a scheduled room). `POST /token` refuses a scheduled room with `room_not_started` (409). A booking unstarted 3 h after `scheduled_for` counts as expired: hidden from `discover` and `mine`, reported as `ended` by `GET /rooms/[slug]`, and refused by `start`.
- **Creating a room** (`POST /rooms`): optional `scheduledFor` (5 min to 30 days ahead), `bannerUrl` (must be a URL returned by `POST /banner`, checked against our bucket prefix), `moderators` (up to 3 @usernames, each must have a profile). Pre-assigned moderators are participant rows with `role = moderator` and `left_at` set, so they hold the role without counting as present.
- **Banners** (`POST /banner`): base64 photo in, resized by `sharp` to a 1200×675 JPEG with EXIF stripped, stored in the public `chautari-banners` bucket, public URL out. Rate limited.
- **Listing**: `GET /discover` (public) returns live rooms and unexpired bookings with `bannerUrl`, `hostUsername`, `hostAvatarUrl` and counts. The Chautari tab refetches it the moment a room is created, goes live or ends: a trigger (`site/supabase/2026-11-chautari-live-list.sql`) broadcasts `{ slug, status }` on the public Realtime channel `chautari-rooms` (event `room_status`), which `useLiveRoomList` listens to only while the tab is focused; the 60 s poll stays as the fallback. `GET /rooms/[slug]` (public) returns details, host and moderators, plus `canStart` when signed in. `GET /rooms/mine` lists live and scheduled rooms the caller hosts or moderates.
- **Push**: a room changing to `live` (including from `scheduled`) fires `send-chautari-live-push` through the `chautari_rooms` database webhook. It alerts only the host's followers with `notify` on, on phones linked to them with Chautari alerts on. There is no "every room" alert.

### Reports, word filter and suspensions

Tables in `site/supabase/2026-11-reader-safety.sql` (local copy `supabase/migrations/20261124000000_reader_safety.sql`): `reader_reports`, `reader_suspensions`, the `is_reader_suspended()` function, and a `reader_profiles` read policy that hides suspended readers from the anon key (so from `search_reader_profiles` too) but not from staff with `reports:review`.
- **Reporting** (`POST /api/reader/report`, Clerk bearer, 20 an hour): `{ reason, details? }` plus one of `{ messageId, roomSlug }`, `{ reportedClerkId, roomSlug }` or `{ reportedUsername }`. Reasons `abuse | harassment | spam | other` (ids in `src/features/reports/reasons.ts`, must match the site's `reportRules.ts`). The server looks up the evidence itself (message text and time, room title, both usernames) and stores a copy, so it survives deletion. Refusals: `cannot_report_self`, `not_found`, `invalid_reason`, `account_suspended`. The app's two-step `ReportForm` (reason, then "Anything to add?") is used by `PersonSheet`, the chat, and the profile page (`app/user/[username].tsx`, "Report @username").
- **Word filter** (site `src/lib/moderation/wordFilter.ts`, list in `blocklist.ts`): runs at write time on chat messages, room titles and descriptions, usernames, display names and bios. A match is refused with `422 blocked_words` and auto-reported (`source = 'filter'`, matched words in `details`). Whole-word matching after undoing leetspeak, stretched and spaced-out letters; ambiguous words (caste names, news vocabulary, double meanings) are deliberately not listed.
- **Suspensions**: decided by staff on the site's `/admin/reports` (capability `reports:review`), which lists reports with filters (status, source, reason, context, reader) and a per-person summary. Suspending ends the reader's rooms, removes them from live ones, hides their profile, chat history, hosted rooms and moderator listings, and marks their open reports actioned; it can be lifted. Every interactive site route calls `refuseIfSuspended` (`site/src/lib/reader/suspension.ts`) and answers `403 account_suspended` with a message carrying the reason and the appeal address; new interactive routes must do the same. Reading stays open. `GET /profile/me` also returns `suspension: { message, since } | null`.

### Reader profiles and follows (`/api/reader/*`)

- `GET /profile/me` returns **404 `profile_missing`** for a signed-in reader with no row. The app's signup gate depends on that 404; don't change it to `200` with `null`.
- `POST /profile/signup` creates the row; `409` with `username_taken` or `profile_exists`. `PATCH /profile/me` accepts only `display_name`, `bio`, `avatar_url`: usernames are immutable.
- The username rule (`^[a-z0-9_]{3,30}$` plus a reserved list) exists in three places that must agree: the database check constraint, `site/src/lib/reader/profile.ts`, and the app's `src/features/profile/validators.ts`.
- `POST /profile/check-username` and `GET /profile/[username]` are public (the first is rate limited). `GET /profile/[username]/follow-status` is public with optional auth: `{ is_following, follower_count, is_self }`.
- `POST /follows` `{ followee_username }` and `DELETE /follows/[username]` are idempotent and return the new `follower_count`; following yourself is `409`.
- `PATCH /follows/[username]` `{ notify }` sets `user_follows.notify`: whether the follower hears about that reader's Chautari rooms (went live, invited you). `404 not_following` if there is no edge. `follow-status` returns `notify`. The app asks right after a follow (`FollowAlertPrompt`); the per-person switch is on the profile.
- `reader_profiles` and `user_follows` allow public `select` and no client writes: all writes use the service role after the Clerk check.

### Newsletter and contact (pre-existing)

- Signup is double opt-in and answers identically whether the address is new, pending or already subscribed (no "you're already on the list" oracle). Without a Resend key the site stores the signup and says no email was sent.
- Contact/tip messages are stored in `contact_messages`; with no database the site returns a prefilled `mailto:` instead.

### Push (this repo's `supabase/`)

- News (`send-breaking-push`, named before "All news" existed; the webhook on `articles` INSERT and UPDATE calls that URL) sends to two audiences that never overlap: phones with `all_news_enabled` get every story published in the last 24 h, once (claimed in `mobile_news_push_log`; a breaking story is styled as breaking); phones with `breaking_enabled` and not `all_news_enabled` get breaking stories, once (claimed in `mobile_push_log`). So an All news reader gets one push per story, never a second for breaking. Its decisions are in `plan.ts`, tested from `tests/newsPushPlan.test.ts`. In the app, the Breaking switch shows as included while All news is on and keeps its stored value for when All news goes off. The push opens the story. Browsers get the same story through the site's separate Web Push (`push_subscriptions`, VAPID), which the app does not use. As of 2026-11-17 the droplet's `.env` has no VAPID keys, so browser push likely isn't sending.
- `mobile_push_tokens` is written only through RPCs (`register_push_token`, `unregister_push_token`, `set_breaking_push_preference`, `set_all_news_push_preference`, `set_chautari_push_preference`, `set_reminder_push_preference`); the anon key cannot read the list. Breaking news, all news, Chautari and reminders are separate opt-ins (`breaking_enabled`, `all_news_enabled`, `chautari_enabled`, `reminders_enabled`; all news covers breaking); the token row exists while any is on. `clerk_user_id` (set only by the site's `/api/reader/push-token`) is how alerts about people reach one reader's phones; the app links after each registration and unlinks before sign-out.
- Each sender dedupes by inserting into a log table keyed on what it notifies about (`mobile_push_log.article_id`, `chautari_push_log.room_id`, `reminder_push_log.sent_on`), and authenticates callers with the `x-webhook-secret` header against its `WEBHOOK_SECRET`. That secret is one project-wide Supabase secret shared by every sender; deploying a function never asks for it and keeps it. Supabase won't show it again, but its value is in plain text in each webhook's HTTP headers and in the `reminder-push` cron command. Rotating it means updating every webhook and the cron job in the same sitting.
- `supabase functions deploy <name> --no-verify-jwt` replaces a function in place under the same URL, so existing webhooks and the cron job pick up new code without being touched. Only a new function needs a new webhook. Run its SQL first.
- `send-reminder-push` is called by `pg_cron` (job `reminder-push`, Tue/Thu/Sat 02:15 UTC = 08:00 NPT), not by a webhook. It skips phones seen in the last 3 days (`last_seen_at`, refreshed on launch and on returning to the app, at most every 12 h) or reminded in the last 4 (`last_reminded_at`).
- `send-chautari-invite-push` is triggered by a webhook on `chautari_invites` INSERT; it claims the row via `notified_at`.
- Look: Android uses `assets/notification-icon.png` (white-on-transparent logo) and `notification-large-icon.png`, set in the `expo-notifications` plugin in `app.json` (native: needs a new build). iOS always shows the app icon. Senders add `richContent.image` (story hero, room banner), `subtitle`, `threadId` and `ttl`.

## Testing constraints

- Vitest runs in `node`; add `// @vitest-environment jsdom` for tests that render providers with `react-dom`.
- Vitest cannot parse `react-native`'s source. A module that imports `react-native` can't be imported in a test: mock it (`vi.mock`, with shared values via `vi.hoisted`) or move the pure logic into a React-free file (e.g. `src/lib/notifications/path.ts`).
- Tests cover data, parsing, state machines and API clients; there is no React Native component renderer configured.

## Lint rules that are enforced

The React hooks lint rules fail the build, not just warn: no reading `ref.current` during render (create `Animated.Value`s with `useMemo`), no impure calls like `Date.now()` in render, no synchronous `setState` in an effect body, and all hooks before any early return.
